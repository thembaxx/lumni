# Next.js 16 Feature Adoption Plan for Lumni

## Current State

- **Next.js**: `^16.2.9` with React `19.2.7` — already on v16, features available but unused
- **Cache Components**: Disabled (`cacheComponents` not in config)
- **React Compiler**: Disabled (`reactCompiler` not in config)
- **PPR**: Not enabled
- **Middleware**: `src/middleware.ts` exists (deprecated, needs rename to `proxy.ts`)
- **Client components**: 532 `"use client"` files — heavily client-rendered SPA
- **Suspense**: 24 boundaries already in place — excellent PPR readiness
- **Memoization**: 657+ manual `useMemo`/`useCallback`/`React.memo` calls
- **View Transitions**: Manual polyfill in `src/lib/utils/view-transition.ts` + `src/hooks/use-navigation-direction.ts`
- **Caching APIs**: Zero usage of `revalidateTag`, `cacheTag`, `'use cache'`, or `force-cache`
- **Turbopack**: Already default (no webpack config)

## Priority 1: Cache Components + PPR (Highest Impact)

**What**: Enable `cacheComponents: true` in `next.config.ts`. This activates:

- `'use cache'` directive for component/function-level caching
- Partial Prerendering (PPR) — static HTML shell served instantly, dynamic content streams in via Suspense
- `<Activity>` for navigation state preservation (routes stay mounted but hidden)

**Why**: Lumni is currently 100% dynamic — every page re-renders on every request. PPR gives instant static shells for all 24+ pages that already have Suspense boundaries. Zero refactoring needed for existing Suspense pages.

**Implementation**:

1. Add `cacheComponents: true` to `next.config.ts`:

```ts
const nextConfig: NextConfig = {
  cacheComponents: true,
  // ...existing config
};
```

2. Add `<Suspense>` to 4 pages missing it:
   - `src/app/[locale]/flashcards/page.tsx` — wrap `<FlashcardsClient>` in `<Suspense fallback={<PageSkeleton />}>`
   - `src/app/[locale]/study-groups/page.tsx` — wrap `<StudyGroupsList>` in `<Suspense fallback={<PageSkeleton />}>`
   - `src/app/[locale]/dashboard/exams/page.tsx` — wrap `<ExamsBrowse>` in `<Suspense fallback={<PageSkeleton />}>`
   - `src/app/q/[id]/page.tsx` — wrap `<SharedQuestionClient>` in `<Suspense fallback={<PageSkeleton />}>`

3. Add `'use cache'` to purely static pages:
   - `src/app/[locale]/terms/page.tsx` — fully static content
   - `src/app/[locale]/privacy/page.tsx` — static with `getTranslations()`
   - `src/app/[locale]/cookie-policy/page.tsx` — static with `getTranslations()`

4. Test navigation state preservation — verify that navigating away from dashboard and back preserves scroll position, expanded tabs, and form state (Activity auto-hides routes).

**Pros**:

- Instant static shells for all existing Suspense pages (dashboard, quiz, settings, admin, auth, study, questions, pronunciation, dictionary, stories, solve)
- Zero refactoring for 20+ pages that already have Suspense
- Activity preserves UI state during navigation (form inputs, expanded sections)
- Dramatically reduces Time to First Byte for page loads
- Pairs perfectly with existing offline-first Dexie architecture

**Cons**:

- Build time may increase slightly (static shell generation)
- Activity keeps routes mounted — need to verify no memory leaks with 8-deep provider nesting
- Pages with `connection()` (UploadThing SSR) need testing
- Must verify `next-intl` middleware works correctly with proxy.ts runtime (Node.js)

**Files to modify**:

- `next.config.ts` — add `cacheComponents: true`
- `src/app/[locale]/flashcards/page.tsx` — add Suspense
- `src/app/[locale]/study-groups/page.tsx` — add Suspense
- `src/app/[locale]/dashboard/exams/page.tsx` — add Suspense
- `src/app/q/[id]/page.tsx` — add Suspense
- `src/app/[locale]/terms/page.tsx` — add `'use cache'`
- `src/app/[locale]/privacy/page.tsx` — add `'use cache'`
- `src/app/[locale]/cookie-policy/page.tsx` — add `'use cache'`

## Priority 2: React Compiler (High Impact, Low Effort)

**What**: Enable `reactCompiler: true` in `next.config.ts` and install `babel-plugin-react-compiler`.

**Why**: 657+ manual `useMemo`/`useCallback`/`React.memo` calls across the codebase. The React Compiler automatically memoizes components, eliminating unnecessary re-renders with zero manual code changes. This is the single biggest DX improvement — it makes the codebase cleaner while improving performance.

**Implementation**:

1. Install the plugin:

```bash
pnpm add -D babel-plugin-react-compiler
```

2. Enable in `next.config.ts`:

```ts
const nextConfig: NextConfig = {
  cacheComponents: true,
  reactCompiler: true,
  // ...existing config
};
```

3. Verify build succeeds — React Compiler uses Babel, which adds compile time.

4. Optional: Gradually remove manual memoization from heaviest files:
   - `src/app/[locale]/exam/[id]/exam-session-client.tsx` (16+ useCallback/useMemo)
   - `src/app/[locale]/flashcards/flashcards-client.tsx` (12+ useCallback/useMemo)
   - `src/hooks/use-gamification.ts` (15+ useCallback/useMemo)
   - `src/lib/quiz/use-quiz.ts` (10+ useCallback/useMemo)
   - `src/components/dashboard/dashboard-client.tsx` (5+ useCallback/useMemo)

**Pros**:

- Zero manual code changes required — just enable and go
- Automatically eliminates 657+ memoization calls
- Reduces bundle size (fewer wrapped functions)
- Improves runtime performance (fewer re-renders)
- Makes codebase cleaner and more maintainable

**Cons**:

- Build time increases (Babel compilation overhead)
- Dev hot-reload may be slightly slower
- Some edge cases with `useEffect` dependencies may need manual review
- Not compatible with all third-party libraries that rely on specific memoization patterns

**Files to modify**:

- `next.config.ts` — add `reactCompiler: true`
- `package.json` — add `babel-plugin-react-compiler` dependency

## Priority 3: middleware.ts → proxy.ts Migration (Migration Task)

**What**: Rename `src/middleware.ts` to `src/proxy.ts` and rename the exported function from `middleware` to `proxy`.

**Why**: `middleware.ts` is deprecated in Next.js 16. The new `proxy.ts` runs on Node.js runtime (not Edge), which is simpler and more consistent. The current middleware handles i18n routing and auth protection — both work identically in proxy.ts.

**Implementation**:

1. Rename file: `src/middleware.ts` → `src/proxy.ts`

2. Rename export:

```ts
// Before
export function middleware(request: NextRequest) { ... }

// After
export function proxy(request: NextRequest) { ... }
```

3. Keep `config` export unchanged (matcher pattern stays the same).

4. Verify `next-intl/middleware` works with Node.js runtime (it should — next-intl supports both Edge and Node.js).

**Pros**:

- Aligns with Next.js 16 conventions
- Node.js runtime is more capable than Edge (full Node.js APIs)
- Clearer naming (proxy = network boundary)
- Required for future Next.js versions

**Cons**:

- `next-intl` middleware must be tested with Node.js runtime
- Auth cookie logic (`a_session_*`) must work in Node.js context
- Must verify no Edge-specific APIs are used in the middleware

**Files to modify**:

- `src/middleware.ts` → `src/proxy.ts` (rename + rename export)

## Priority 4: Enhanced Navigation (Automatic, Zero Effort)

**What**: Next.js 16 automatically optimizes navigation with:

- **Layout deduplication**: Shared layouts downloaded once (not per-link)
- **Incremental prefetching**: Only missing parts prefetched
- **Viewport-aware prefetching**: Links prefetched on hover/viewport entry
- **Cancellation**: Prefetch cancelled when link leaves viewport

**Why**: The codebase has 27+ Link components and 131+ router calls. These automatic optimizations reduce network transfer dramatically — especially for the sidebar with 50+ navigation links.

**Implementation**: **None required** — these are automatic framework improvements.

**However**, the existing manual View Transition polyfill can be replaced:

1. Replace `src/lib/utils/view-transition.ts` and `src/hooks/use-view-transition.ts` with React 19.2 built-in `<ViewTransition>` component.

2. Simplify `src/hooks/use-navigation-direction.ts` to use `useTransition()` + `router.push()` instead of manual `startViewTransition()`.

**Pros**:

- Zero code changes for prefetching improvements
- Dramatically reduces network transfer for navigation
- View Transitions become native React 19.2 feature (no polyfill needed)

**Cons**:

- More individual prefetch requests (but lower total transfer)
- View Transition migration requires careful testing of existing animations
- Some custom animation logic in `useNavigationDirection` may need adaptation

**Files to modify**:

- `src/lib/utils/view-transition.ts` — simplify or remove
- `src/hooks/use-view-transition.ts` — replace with React 19.2 API
- `src/hooks/use-navigation-direction.ts` — simplify with native View Transitions

### Priority 9: Activity for Dashboard Tab State Preservation (High Impact)

**What**: Replace conditional rendering (`{activeTab === "today" && <TodayTab />}`) with `<Activity>` in the dashboard to preserve tab state across switches.

**Why**: Currently when users switch between Today/Practice/Analytics tabs, the previous tab unmounts completely — losing scroll position, expanded sections, loaded data, and any in-progress interactions. With Activity, tabs stay mounted but hidden (`display: none`), preserving all state.

**Implementation**:

In `src/components/dashboard/dashboard-content.tsx` (lines 92-101), replace:

```tsx
{
  activeTab === "today" && <HeroBanner />;
}
{
  activeTab === "today" && <TodayTab />;
}
{
  activeTab === "practice" && <PracticeTab />;
}
{
  activeTab === "analytics" && <AnalyticsTab />;
}
```

With:

```tsx
<Activity mode={activeTab === "today" ? "visible" : "hidden"}>
  <HeroBanner />
  <TodayTab />
</Activity>
<Activity mode={activeTab === "practice" ? "visible" : "hidden"}>
  <PracticeTab onStartQuiz={onStartQuiz} />
</Activity>
<Activity mode={activeTab === "analytics" ? "visible" : "hidden"}>
  <AnalyticsTab />
</Activity>
```

**Pros**:

- Tab state preserved (scroll position, expanded sections, loaded analytics)
- Faster tab switching (no re-mount/re-render)
- Pre-rendering: hidden tabs load data at lower priority in background
- Better UX for users who frequently switch tabs

**Cons**:

- Memory usage increases (3 tabs always mounted)
- Need to handle media cleanup (timers, video) in hidden tabs
- Test selectors may need visibility-aware queries

**Files to modify**:

- `src/components/dashboard/dashboard-content.tsx` — replace conditional rendering with Activity
- `src/components/dashboard/__tests__/dashboard-content.test.tsx` — update test selectors

### Priority 13: cacheLife Profiles for Dynamic Content (Medium Impact)

**What**: Add `cacheLife` profiles to pages that fetch data, so cached content is served instantly while background revalidation keeps it fresh.

**Why**: Currently all data is fetched fresh on every request. With `cacheLife`, we can serve stale content instantly while revalidating in the background — dramatically improving perceived performance.

**Implementation**:

Add cache profiles to `next.config.ts`:

```ts
const nextConfig: NextConfig = {
  cacheComponents: true,
  reactCompiler: true,
  cacheLife: {
    realtime: { stale: 30, revalidate: 1, expire: 60 }, // live data
    frequent: { stale: 300, revalidate: 60, expire: 3600 }, // leaderboard, analytics
    moderate: { stale: 3600, revalidate: 900, expire: 86400 }, // study guides, exam dates
    stable: { stale: 86400, revalidate: 604800, expire: 2592000 }, // terms, privacy
  },
};
```

Then apply to specific functions:

```tsx
// src/app/[locale]/leaderboard/page.tsx
async function LeaderboardPage() {
  "use cache";
  cacheLife("frequent"); // revalidate every minute
  // ...
}

// src/app/[locale]/study-guide/page.tsx
async function StudyGuidePage() {
  "use cache";
  cacheLife("moderate"); // revalidate every 15 minutes
  // ...
}
```

**Pros**:

- Instant page loads for previously visited pages
- Background revalidation keeps content fresh
- Reduces server load (fewer full renders)
- Fine-grained control per content type

**Cons**:

- Need to identify which pages benefit from caching
- Stale content risk (need appropriate TTLs)
- `use cache` requires async functions (refactoring)

**Files to modify**:

- `next.config.ts` — add cacheLife profiles
- Multiple page files — add `'use cache'` + `cacheLife()`

### Priority 14: useEffectEvent for Stable Event References (Low-Medium Impact)

**What**: Replace `useCallback` wrappers around event handlers with `useEffectEvent` for simpler, more stable references.

**Why**: `useEffectEvent` extracts non-reactive logic from Effects, eliminating the need for `useCallback` in many cases. The codebase already uses it in 2 files — expand to more.

**Candidates**:

- `src/hooks/use-navigation-direction.ts` — navigation direction callback
- `src/hooks/use-swipe-deck.ts` — swipe state callbacks
- `src/components/flashcard/swipeable-card.tsx` — drag handlers
- `src/components/dashboard/dashboard-client.tsx` — tab change handler

**Implementation**:

```tsx
// Before
const handleTabChange = useCallback((tab: TabValue) => {
  setActiveTab(tab);
  trackEvent("tab_change", { tab });
}, []);

// After
const handleTabChange = useEffectEvent((tab: TabValue) => {
  setActiveTab(tab);
  trackEvent("tab_change", { tab });
});
```

**Pros**:

- Simpler code (no dependency arrays)
- More stable references (no stale closures)
- Cleaner Effect dependencies

**Cons**:

- Only available in React 19.2+ (already using it)
- Not a replacement for all useCallback (only for event handlers)

**Files to modify**:

- 4-6 files (see candidates above)
