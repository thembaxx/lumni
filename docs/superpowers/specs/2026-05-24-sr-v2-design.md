# Spaced Repetition v2 — Algorithm Quality Upgrade

**Date:** 2026-05-24
**Status:** Approved Design

## Problem

SR v1 has a solid foundation (SM-2 + FSRS algorithms, Dexie persistence, review history) but the review experience is simplified to a binary choice: Known (quality 4) or Review (quality 1). There is no graduated learning phase for new cards, no protection against ease-hell or leech cards, and no daily card budget limits.

## Scope

Algorithm quality improvements only. No deck organization, card templates, image/media support, server sync, push notifications, or stats dashboard (those are separate future work).

## Components

### 1. Full 6-Quality Grading

**Current state:** `flashcards-active.tsx` shows two buttons — "I Know This" maps to quality 4, "Review Later" maps to quality 1.

**Target:** After card flip, show a 6-button quality picker matching the SM-2 scale:
- **0** — Complete Blackout (couldn't recall at all)
- **1** — Incorrect, remembered after seeing answer
- **2** — Incorrect, answer seemed easy
- **3** — Correct with serious difficulty
- **4** — Correct with some hesitation
- **5** — Correct instantly

Each button shows the label + a brief description. The existing `SM2StudySession` component (`src/components/study/sm2-study-session.tsx`) has this UI pattern already — we port the button group styling to `flashcards-active.tsx`.

**Behavior:**
- Qualities 0-2 → card treated as failed (lapses++, reset interval to learning step 0)
- Qualities 3-5 → card treated as passed (advance learning step or increment repetitions)
- After selection, show a brief animation, then advance to next card

### 2. Configurable Learning Steps

**Current state:** New cards go directly to SM-2's `interval = 1` (1 day). No intra-session graduated intervals.

**Target:** New cards graduate through a configurable sequence of steps before entering the standard schedule.

**Implementation:**
- `learningStep` field on `FlashcardSM2` (integer, -1 = graduated, 0 = first step)
- Default steps array: `[1, 10, 1440]` (1 minute, 10 minutes, 1 day in minutes)
- On pass (quality >= 3): advance to next step
- On fail (quality < 3): reset to step 0
- On graduating past last step: `learningStep = -1`, card enters standard SM-2/FSRS scheduling with `interval = 1`
- Steps array configurable via settings (comma-separated minutes)

**Learning steps state machine:**
```
New card (repetitions=0, interval=0, learningStep=0)
  → Pass: advance learningStep
    → If last step: graduate (learningStep=-1), compute next review as day 1
    → Otherwise: nextReview = now + stepDuration, same card stays in learning
  → Fail: reset to learningStep=0, nextReview = now + stepDuration
```

### 3. Ease-Hell Recovery

**Current state:** A card that enters ease-hell (e.g., EF=1.3) stays there permanently. No mechanism to recover.

**Target:** After N consecutive successful reviews (quality >= 3) at any interval, apply a small ease factor bonus.

**Default config:**
- Consecutive passes required: 3
- Ease bonus: +0.15

**Implementation in `repository.review()`:**
- Track consecutive successful reviews via the `lapses` counter being unchanged + quality >= 3
- When count reaches threshold, `easeFactor += easeHellBoost`
- Cap EF at a max (default: no cap, but EF never exceeds 5.0 implicitly by formula)

### 4. Leech Detection

**Current state:** `lapses` counter increments on each failure but has no consequences.

**Target:** Cards with `lapses >= threshold` are flagged and automatically suspended.

**Default config:**
- Leech threshold: 8 lapses
- Leech action: `suspend` (options: suspend, bury, tag-only)
- `leeched: boolean` field prevents repeated notifications

**Implementation:**
- On fail (quality < 3): after `repository.review()` increments lapses, check `lapses >= leechThreshold && !card.leeched`
- If leech detected: set `card.leeched = true`, perform configured action
- `suspend`: set `card.status = "suspended"`
- `bury`: set `card.status = "buried"` (invisible until manually reviewed)
- `tag-only`: set `card.leeched = true` but keep `status = "active"` (visible in browse with badge)

### 5. Daily Card Limits

**Current state:** `getNewCards()` hardcodes limit 20, no review cap.

**Target:** Configurable daily budgets for new cards and reviews. Budgets reset daily.

**Default config:**
- Max new cards per day: 20
- Max reviews per day: 200

**Implementation:**
- Daily budget stored in localStorage as `lumni_sr_budget_{date}` or in Dexie
- Budget reset checked on session start by comparing stored date to today
- `getDueCards()` capped at `maxReviews` per day
- `getNewCards()` capped at `maxNew` per day (replaces hardcoded 20)
- Cards exceeding budget show "Come back tomorrow" and are skipped
- User can override the limit on a per-session basis ("Study more anyway")

## Data Model Changes

### FlashcardSM2 (new fields)

```typescript
interface FlashcardSM2 {
  // ... existing fields ...
  learningStep: number;  // -1 = graduated, 0+ = current learning step index
  leeched: boolean;      // true if card has been flagged as leech
}
```

### SRSettings (new, persisted in localStorage)

```typescript
interface SRSettings {
  learningSteps: number[];        // minutes per step, default [1, 10, 1440]
  dailyNewLimit: number;          // default 20
  dailyReviewLimit: number;       // default 200
  leechThreshold: number;         // default 8
  leechAction: "suspend" | "bury" | "tag-only";  // default "suspend"
  easeHellPasses: number;         // consecutive passes for boost, default 3
  easeHellBoost: number;          // EF bonus, default 0.15
}
```

### Dexie migration (v14)

```
flashcards: "&id, subject, topic, nextReview, easeFactor, interval, repetitions, status, learningStep, leeched"
```

## Non-Goals

- No card decks/tags/hierarchy
- No card templates (cloze, reverse)
- No image/media in card content
- No Appwrite server sync for flashcards
- No push notification reminders
- No FSRS optimizer
- No statistics dashboard
- No card editing UI from session (use existing browse page)
