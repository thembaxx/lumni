1. Three handler factories where two are shallow

Strong
Files
  • src/lib/api/create-route-handler.ts (134 lines)
  • src/lib/api/create-ai-handler.ts (48 lines)
  • src/lib/api/engine-handler.ts (43 lines)
  • ~20 engine routes + ~10 AI-budget routes that consume these
Problem

createAIHandler and createEngineHandler are nearly identical wrappers over createRouteHandler. Both set auth: "none", both pass budget types, both call the base factory. They differ only in whether they pass requestId and how execute(…) receives its arguments. The interface of each wrapper is almost as complex as the implementation — neither is deep. The deletion test: removing either spreads ~3 lines of config across ~10+ callers without concentrating any behaviour. The factories are pass-throughs.

Solution

Merge the two wrapper concerns into createRouteHandler's config shape directly — add passRequestId and executeHelpers as optional fields so callers pick their flavour from one factory. Remove createAIHandler and createEngineHandler as separate exports. The interface shrinks; callers see one factory with config knobs instead of three factories to choose among.

Benefits
  • Locality: auth-mode, budget, requestId wiring lives in one place
  • Leverage: one factory replaces three; new route types just add config
  • Tests: createRouteHandler tests cover all paths automatically
  • Migration: each route changes createAIHandler(config) → createRouteHandler({...config, budget: config.budgetType}) — trivially mechanical

2. Quiz-packs route is hand-rolled outside the factory seam

Strong
Files
  • src/app/api/quiz-packs/generate/route.ts (80 lines)
  • Compared to: src/app/api/engine/generate/route.ts (37 lines)
Problem

The quiz-packs generate route has its own auth check, its own try/catch, its own NextResponse.json() calls, and manual dynamic imports. Every other engine-like route uses createEngineHandler and gets consistent error handling, budget tracking, body parsing, and validation for free. This route duplicates ~43 lines of boilerplate that the factory already provides. The deletion test: replacing this with the factory doesn't concentrate complexity — the factory already exists. It just removes a duplicate implementation.

More subtly: this route doesn't budget-track its AI calls (engine.generate() consumes budget but the route never calls trackUsage or checkBudget). If budget limits are enforced, quiz-pack generation silently bypasses them.

Solution

Migrate to createAIHandler (or the merged factory from Candidate 1). The route shrinks from 80 lines to ~25. Budget tracking, auth, and error wrapping come for free. The dynamic imports stay but the boilerplate disappears.

Benefits
  • Leverage: the factory earns its keep the moment a second route uses it
  • Locality: bug fixes in error handling, budget tracking, or validation apply to quiz-packs without editing the route
  • Seam: if quiz-packs later needs rate limiting or audit logging, the config toggle exists

3. GradeEventBus has dual import paths — the barrel re-export is pure indirection

Worth exploring
Files
  • src/lib/grade-event-bus/index.ts (37 lines)
  • src/lib/services/index.ts (re-exports GradeEvent and GradeEventBus)
  • src/lib/orchestrator/grading.ts (direct import from grade-event-bus)
Problem

src/lib/services/index.ts re-exports GradeEvent and GradeEventBus from grade-event-bus. But src/lib/orchestrator/grading.ts imports from grade-event-bus directly. Two valid import paths exist for the same module. The deletion test: remove the re-export from services/index.ts and zero modules break (the orchestrator uses the direct path). The re-export adds no leverage — it's pure indirection that makes the module graph harder to trace.

Solution

Remove the GradeEvent and GradeEventBus re-exports from the services barrel. All consumers import directly from @/lib/grade-event-bus. If the grade event bus is genuinely a cross-cutting concern, document it as such in CONTEXT.md rather than wiring it through the services barrel.

Benefits
  • Locality: one canonical import path for the module
  • Seam: the module's interface is at its own directory, not filtered through a barrel
  • Low effort, high hygiene: removing one re-export line

5. Dashboard content component pulls 29 imports — an undigested domain

Worth exploring
Files
  • src/components/dashboard/dashboard-content.tsx (29 imports, 288 lines)
  • src/components/dashboard/dashboard-client.tsx (19 imports, 206 lines)
  • src/components/dashboard/practice/ (12 files, each 14-17 imports)
Problem

dashboard-content.tsx has more imports than any other component in the codebase (29). It's a monolith — not in line count (288 is manageable) but in dependency breadth. Understanding what the dashboard does means tracing 29 import edges. The component is deep (it renders the entire dashboard) but that depth comes at the cost of locality: any change to dashboard data fetching, a sub-section's layout, or a new metric requires editing dashboard-content.tsx and understanding all 29 dependencies.

ADR-0002 (component decomposition) proposes atomic design for this exact problem. The dashboard is the largest violation of that guidance in the codebase. This is not a contradiction of ADR-0002 — it's the primary motivation for it.

Solution

Not a single refactor — a progressive decomposition programme. Each dashboard section (competency overview, study plan, today focus, stats) becomes a module with its own data-fetching interface. dashboard-content.tsx becomes a thin orchestrator that composes these modules. The 29 imports shrink to ~6-7 sub-module imports. Each sub-module is independently testable via its own interface.

This is a medium-term programme, not a single PR.

Benefits
  • Locality: dashboard section changes stay in that section's module
  • Leverage: the orchestrator interface is <DashboardContent /> — unchanged — but internal leverage increases as each sub-module earns its keep
  • Seam: each dashboard section becomes a place behaviour can be altered without editing dashboard-content.tsx
  • Tests: sub-modules testable via their props/interface instead of requiring the full dashboard render

Top recommendation

Tackle Candidate 1 first: merge the three handler factories into one.

Here's why:

  1. Highest leverage per change: merging the factories affects ~30 route files. The interface shrinks from three factory functions to one. The deletion test is definitive — both wrappers are pure pass-throughs.
  2. Enables Candidate 2: once the merged factory handles all config shapes, the quiz-packs route can adopt it in one mechanical PR.
  3. Pattern completeness: Session 8 already migrated 5 routes to createRouteHandler. Completing the adoption (including via the merged factory) means zero hand-rolled routes exist in the API surface.
  4. Zero behavioural risk: the wrapper functions are perfectly symmetric — the merge is pure config transformation. No logic changes.

Estimated effort: 1-2 hours for the factory merge + 30 minutes per route group (~15 groups) = a day's work. Can be done incrementally: merge the factories first, then adopt routes one at a time.
