Problem

Services import offlineDB directly from schema.ts, bypassing the existing repository layer. This means: (a) testing a service requires an IndexedDB instance, (b) there's no seam to swap Dexie for another backend, and (c) repository abstractions exist but are irrelevant to the service layer.

Solution

Give each service its repository (or repository interface) as a constructor parameter. Services stop importing offlineDB directly. Repositories become the single seam between business logic and persistence.

Wins

  • Seam becomes real: two adapters — Dexie in prod, in-memory in tests
  • Interface is the test surface: test a service without IndexedDB — mock the repository
  • Locality: Dexie schema changes affect only the repository layer, not all 10 services

Problem

Strong

Migrate all routes to createRouteHandler

This is the highest-leverage refactor. 85 of 100 route files don't use the factory, duplicating ~2k lines of boilerplate across three coexisting patterns. The factory already works — it just needs params and webhook support for the remaining 3 edge-case routes. The 19 half-migrated routes (withRateLimit wrapper) are trivial mechanical migrations. Tackle by route-group: sibling routes of already-migrated handlers first (admin/exams/*, exam-sessions/*, engine/*), then auth (4 routes), then the bulk (66 remaining).

Why this over the others: Every PR touches a route handler. Every route currently duplicates auth, validation, error handling, and response construction. Fixing the factory eliminates that tax permanently. The data-layer seam (candidate 5) and service unification (candidate 4) are close seconds, but they affect fewer call sites and the existing code works. The route migration affects every frontend-backend interaction.
